# OpenRevo 后续更新计划

制定日期：2026-10-18；进度更新：2026-10-22。历史基线为已发布的 [v0.1.0](https://github.com/Qrzzzz/OpenRevo/releases/tag/v0.1.0)，提交 `384fbdc`。用户随后要求将原 0.1.1 维护内容合并到 0.2.0。实际实现与验收见 [0.2.0 审计](v0.2.0-audit.md)，本计划中的后续控制能力仍不代表已实现或验收。

## 目标与基线

继续还原本机机械革命控制中心的功能和通信协议，沿用 Windows 11 原生界面。开发优先级由协议证据、实际用途和可恢复性决定。

v0.1.0 已完成本机识别、受限 MQTT 查询、监控状态展示、能力清单、原始 JSON 和诊断导出；29 项核心检查、本机原生交互、GitHub CI 与发布包校验通过。具体证据见 [MVP 审计](mvp-audit.md)。

当前仍依赖原厂 GCUBridge / GCUService。适用范围仅覆盖已审计的主板、BIOS 和服务指纹。核心服务的受保护方法体尚未完整恢复；控制命令的发送格式、能力位和 IOCTL 名称不能替代本机控制行为的验证。

## 已合并到 v0.2.0：稳定性与诊断

1. 补充服务暂时不可用、连接中断、重复实例、长时间监控、休眠恢复和供电变化的观察记录。先复现问题，再决定具体修复，避免重写已经通过验证的会话逻辑。
2. 完善错误分类：区分未审计版本、服务不可用、认证 / 订阅失败、槽位占用和主题未更新。缺失传感器继续显示未知，不用其他轮次的数据补齐。
3. 检查能力刷新后的降级行为：服务未就绪或身份字段不再匹配时，停止后续监控启用请求，保留历史并要求重新确认连接；不能永久沿用首次通过的能力判断。
4. 验证系统时间调整对新鲜度的影响，使用适合计算经过时间的时钟，保留 UTC 时间用于诊断。保活与其他主题更新不能刷新单个传感器的年龄。
5. 改善首次启动的键盘焦点与可达性，复验 Ctrl+R / Ctrl+S、断开状态和导出失败反馈；明确标题栏焦点下的快捷键行为。
6. 更新 CI 中出现 Node.js 20 弃用告警的资产上传 / 下载 Action，选用原生支持当前运行时的版本并固定提交；保留锁定 SDK、依赖锁文件和发布前下载校验。

验收：原有 29 项检查继续通过，新增测试只覆盖实际新增或修复的行为；完成本机原生交互和上述可安排的实机场景，未执行项明确列出。CI、打包、资产下载与 SHA256 核验均通过后发布补丁版。此版本维持三种固定查询 / 采样请求。

## v0.2.0：协议和能力证据

1. 建立统一的机器可读协议索引，把现有静态命令目录、三种运行时请求和真实响应关联起来。分别记录发送端、服务端处理、实机观察和恢复验证，避免用一个“支持”标志覆盖不同证据层次。
2. 每条消息记录主题、Action、字段类型、单位是否确认、RETAIN、触发条件、返回状态、失败表现和证据文件摘要。保留未知字段，凭据及原始本机诊断不进入公开仓库。
3. 优先恢复状态读取及模式切换相关的路由、输入校验和实际处理分支；分析对象限定为目标路径。其他受保护方法继续明确标为未恢复，不承诺一次还原整个核心服务。
4. 将当前机型条件整理为可审计的配置，关联主板、BIOS、服务指纹、项目 ID 与能力编码。先表达现有适用范围，再按独立证据增加配置；不通过放宽指纹来扩大兼容性。
5. 对同一机型观察空闲 / 负载、AC / DC、原厂前端开 / 关、休眠前 / 后的状态差异。不能用 CI 或模拟服务器结果代替这些观察。
6. 针对 TGP 目标 140、同一响应上限 115 的矛盾建立专项记录，确认字段所处模式、编码和含义；在解释成立前，继续保留原值和矛盾提示。

验收：运行时每条允许发送的请求都有可追溯的契约与证据；已知、未知和未执行项能分别查询；新增机型配置必须有对应实机结果。控制候选形成单独的审计结论与试验方案，本版本仍不开放硬件写入。

## v0.3.0：首个控制闭环（历史方案）

最初候选为原厂办公／均衡模式。实际 0.3.0 已扩展到四模式，支持原厂已保存的自定义配置，未开放参数编辑。以下为初期方案；实际范围与证据以 0.3.0 审计记录为准。模式切换联动散热与功耗。

开放前必须明确以下内容：

- 本机适用条件、AC / DC 限制、实际处理分支、参数与联动范围。
- 原模式及相关状态的读取方法，以及经验证的显式恢复路径。
- 业务成功的回读判据、等待时间、失败和部分成功的表现；MQTT 发送成功不等于硬件生效。
- 与原厂前端、服务周期覆盖的相互影响。OpenRevo 的占用锁只约束自身实例，不能宣称已与原厂程序实现互斥。
- 断线、取消、退出和休眠后的行为；不周期写入，不在重连时自动重放控制命令，结果不明时不盲目重试。

实现顺序为：补全审计 → 安排独立的实机控制验证 → 确认恢复 → 实现受限接口 → 原生界面操作与回读 → 发布。每种操作使用明确的类型和字段约束，不引入任意主题发布、通用 EC 写入或未知参数试发。

验收：切换和恢复均有本机前后状态与时间记录；联动符合已确认契约，干扰和失败时不会持续争抢控制权。若无法建立可靠的结果判据或恢复路径，则延后控制版本，继续发布已验证的读取改进。

## 长期：独立后台

先评估 Windows 标准接口能覆盖的读取能力，再研究确有必要替代的厂商后台路径。直接硬件访问需要先确认 IOCTL 缓冲区布局、输入输出长度、同步、超时、错误返回、机型分支和恢复方式。现有 19 个导出及常量核对结果只作为线索。

“减少对原厂后台的依赖”单独验收，不能用关闭原厂前端后仍能读取状态来证明。保持原厂服务可用是当前阶段的前提，不安排自动卸载、停用服务或新增内核驱动。

## 执行与发布

每次更新先选定一个版本范围，再落实实现与验收。软件测试、本机行为、原生界面、CI 和公开发布资产分别记录结果；未执行或失败的项目不写为通过。硬件控制试验另行安排，制定本计划不等于开始执行写入试验。

后续版本继续使用现有发布流程：源码与测试完成 → 本机必要验收 → main CI 通过 → 版本标签 → Release 构建 → 上传草稿资产 → 下载校验 → 正式发布。版本号、发布说明和标签必须一致。

0.9.0 已完成功能冻结与已记录的正常使用验证，1.0 按 `v1.0-acceptance.md` 收尾，不要求新增硬件参数写入或完整恢复受保护业务入口。

四种模式的已审计语义命令现由独立门控开放；此前仅查询的描述作为历史基线保留。完整条件、实机成功与中止记录、恢复限制见 [0.3.0 审计](v0.3.0-audit.md)。统一目录的 controlRequests 为当前受限入口，历史发送端目录不构成可执行白名单。
